## 修复

- PCM 队列达到目标上界时，音频线程等待设备释放空间，不继续解码后丢弃新声音。
  网络接收回调不等待播放设备，压缩队列仍有包数和 120ms 时长双上限。
- 本地限时丢弃的旧包不会再被当作网络缺口连续填静音，直接重锚已有真实音频。
- 缺口占位最多连续 30ms，然后恢复已有真实包，不长时间追赶移动的队头。
  这是有界静音占位，不宣称实现了 Opus 内置 PLC/FEC。
- 根据 Opus TOC 计算真实包时长，启动、排队和缺口时间不再统一猜为 10ms。
  参考 [RFC 6716 第 3 节](https://www.rfc-editor.org/rfc/rfc6716#section-3)。
- 修复重新预缓冲时，第一块 PCM 被设备播放后又中断同一轮补充、反复重缓冲的状态问题。
  不为普通断粮反复 Stop/Start 音频设备，不重置已播放采样时钟。
- zmd 专属启用断粮后的抗抖目标：60 → 80 → 100ms，封顶 100ms；
  ys 等其他路径不启用这个自适应增大，但共用队列与缺口恢复修复。
- 保持原来的低带宽音频请求和音量处理，不改变视频画质、帧率、登录或手柄协议。
  16kbps 是接收偏好，不保证云端实际采用该码率。

所有队列保持有界；为兼容 2.5ms 小包，audout 页池从 24 增至 64 页，
每页 16KiB，合计 1MiB（比原实现增加 640KiB）。时长背压仍生效，不代表允许堆积 64 个长包。

## 新诊断

已有透明 HUD 保持简洁。新增计数在周期安全快照中输出，不逐包或逐帧写日志：

- 正常解码采样、静音占位采样、迟到包、接收队列限时丢弃。
- 序号重锚、等待播放空间次数、设备队列时长上界、当前抗抖目标。
- 实际包时长、最长收包间隔、音频线程最长间隔、最长 hwopus 解码耗时。

“等待空间”不是丢包，“收包间隔”不是网络丢包数；新增计数用于区分调度、缓冲和传输原因。

## 验证边界

离线生产代码测试覆盖时间线、换源、断粮重补、设备失败、突发背压、溢出恢复、长缺口重锚、
20ms / 2.5ms / 120ms 包和自适应缓冲。相关主机回归及 Switch 构建结果见随包构建记录。

本版没有进行更新后的真实 Switch 听感验收，不能宣称断续已经完全消失。
需在相同网络、相同设置下连续游玩，比较新日志的断粮、输出丢弃、正常解码与静音占位增量。
较长收包／调度停顿仍可能听到中断；本版目标是避免本地队列放大成持续静音。

0.2.113 的 SDK 配置持久化与移除本地改键继续保留；游戏内键位跨会话结果仍未验收。
